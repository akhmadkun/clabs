LAB-011 — STEP-BY-STEP SOLUTION GUIDE

0. PRE-FLIGHT
- Stop any other OSPF lab using these VLAN IDs and prefixes.
- Keep the user-managed `br-univ`; never delete or recreate it.
- Follow CLEANUP-BEFORE-LAB011.txt, then load the correct baseline profiles and commit them on R1–R5.
- If the baseline is not healthy, fix that first. Do not proceed with summarization until the four intended adjacencies are Full.

1. VERIFY THE BASELINE
Commands (operational mode):
  run show interfaces terse | match "eth1\\.(12|13|34|45)"
  run show ospf interface
  run show ospf neighbor
  run show route 192.168.11.3/32
  run show route 192.168.11.4/32
  run show route 192.168.11.5/32

Expected baseline:
- R1–R2, R1–R3, R3–R4, and R4–R5 each have OSPF adjacency Full.
- R2 learns all three service /32 loopbacks through OSPF, via R1.
- R2 has no 192.168.11.0/24 summary yet.

2. CONFIGURE THE AREA RANGE ON R1
At [edit] on R1:
  set protocols ospf area 0.0.0.1 area-range 192.168.11.0/24
  commit check
  commit

The range is configured under Area 1 on the ABR R1. The area-range statement summarizes matching intra-area routes when advertising them across the area boundary. The matching specifics are filtered at that boundary and the summary is advertised in their place.

Optional filter-only behavior (official `area-range restrict`):
  delete protocols ospf area 0.0.0.1 area-range 192.168.11.0/24
  set protocols ospf area 0.0.0.1 area-range 192.168.11.0/24 restrict
  commit check
  commit

In this mode, the specified summary is NOT advertised and routes in the range are suppressed from the other area. Verify on R2 that neither the /32 specifics nor the /24 summary is present. Restore normal summarization before finishing:
  delete protocols ospf area 0.0.0.1 area-range 192.168.11.0/24 restrict
  set protocols ospf area 0.0.0.1 area-range 192.168.11.0/24
  commit check
  commit

3. VERIFY ON R2
From operational mode on R2:
  run show route 192.168.11.0/24
  run show route 192.168.11.3/32
  run show route 192.168.11.4/32
  run show route 192.168.11.5/32
  run show route protocol ospf
  run show ospf database area 0.0.0.0

Expected result:
- 192.168.11.0/24 appears as an OSPF interarea route.
- The three matching /32 routes are no longer advertised individually into Area 0.
- The Area 0 LSDB includes the summary network advertisement for 192.168.11.0/24.
- Router-ID loopbacks (10.1.1.3/32, 10.1.1.4/32, 10.1.1.5/32) are outside the range and should remain separately available.

If the CLI's `show ospf database area ...` form differs on the installed image, run `run show ospf database` and inspect Area 0's Network Summary entries. Do not infer success from the configuration line alone; verify the resulting route/LSDB.

4. TEST REVERSIBILITY
On R1:
  delete protocols ospf area 0.0.0.1 area-range 192.168.11.0/24
  commit check
  commit

On R2, verify individual service /32 routes return. Then restore the final lab state on R1:
  set protocols ospf area 0.0.0.1 area-range 192.168.11.0/24
  commit check
  commit

5. FINAL CHECK
Run the Task 3 checks on R2 and confirm the summary route is present, the more-specific /32s are absent as OSPF routes, and other routes remain reachable.

COMMON PITFALLS
- Configuring the range under Area 0 instead of the source Area 1 on R1.
- Leaving previous OSPFv3/virtual-link configuration active from LAB-010.
- Reusing VLANs concurrently with another lab on `br-univ`.
- Forgetting that this lab's prefixes are OSPFv2 IPv4, so use `show ospf`/`show route` rather than `show ospf3`.
- Treating `commit` success as proof of route summarization; the routing table and LSDB must confirm behavior.
