LAB-010 - OSPFv3 VIRTUAL LINKS
TASK-ONLY WORKSHEET

SOURCE BASIS
Junos OS OSPF User Guide, Chapter 4, “Example: Configuring OSPFv3 Virtual Links”, printed pages 159-174. The source uses OSPFv3 IPv6 unicast, explains two virtual links through Area 1, and verifies with show ospf3 interface/neighbor/database/route commands.

OBJECTIVE
Configure an OSPFv3 network with two noncontiguous Area 0 segments and Area 2 behind R6. Establish two virtual links through a normal Area 1 and prove that they restore backbone connectivity and allow OSPFv3 IPv6 loopback routes to propagate.

TOPOLOGY / LINK PLAN
- Area 0 segment A: R1-R4 on VLAN 14 / eth1.14.
- Area 0 segment B: R2-R3 on VLAN 23 / eth1.23.
- Transit Area 1 triangle: R3-R4 on VLAN 34 / eth1.34; R3-R6 on VLAN 36 / eth1.36; R4-R6 on VLAN 46 / eth1.46.
- Remote Area 2: R6-R10 on VLAN 610 / eth1.610.
- Virtual link A: R3 <-> R4, transit Area 1; bridges the disconnected Area 0 segments.
- Virtual link B: R4 <-> R6, transit Area 1; connects R6 and the remote Area 2 to Area 0.

TASK 0 - CLEAN AND LOAD ADDRESSING BASELINE
1. Follow CLEANUP-BEFORE-LAB010.txt. Do not modify jun-ospf.clab.yml or br-univ.
2. Load the matching addressing profile on R1, R2, R3, R4, R6 and R10.
3. Run `commit check` and `commit` on each router.
4. Check that each listed eth1.<VLAN> subinterface has the planned IPv6 address, VLAN ID equals the unit number, and each router has its unique router ID and IPv6 loopback.

ACCEPTANCE CRITERIA
- R1-R4 use VLAN/unit 14; R2-R3 use 23; R3-R4 use 34; R3-R6 use 36; R4-R6 use 46; R6-R10 use 610.
- Addressing matches ADDRESS-PLAN.txt exactly.
- No OSPF protocol is enabled yet and no OSPFv3 IPv4-unicast realm is configured.
- Router IDs are unique: 10.1.1.1, .2, .3, .4, .6, .10.

TASK 1 - BUILD THE PHYSICAL OSPFv3 AREAS (NO VIRTUAL LINKS YET)
Configure `protocols ospf3` for IPv6 unicast only:
- R1: Area 0 on eth1.14; lo0.0 passive in Area 0.
- R2: Area 0 on eth1.23; lo0.0 passive in Area 0.
- R3: Area 0 on eth1.23; Area 1 on eth1.34 and eth1.36; lo0.0 passive in Area 1.
- R4: Area 0 on eth1.14; Area 1 on eth1.34 and eth1.46; lo0.0 passive in Area 1.
- R6: Area 1 on eth1.36 and eth1.46; Area 2 on eth1.610; lo0.0 passive in Area 1.
- R10: Area 2 on eth1.610; lo0.0 passive in Area 2.
Run `commit check` and `commit` on all six routers.

Verify physical OSPFv3 neighbors before configuring any virtual links. Capture:
  run show ospf3 interface
  run show ospf3 neighbor
  run show ospf3 database
  run show ospf3 route
Record which remote loopback routes are present and missing on R1 and R10. Do not use static routes to simulate success.

ACCEPTANCE CRITERIA
- The six physical links form OSPFv3 IPv6-unicast adjacencies in the specified areas.
- Area 1 is a normal transit area; do not configure it as stub, totally stubby, or NSSA.
- There are no virtual-link statements yet.
- The initial route-table/LSDB state has been recorded for comparison after the virtual links are configured.

TASK 2 - CONFIGURE THE VIRTUAL LINKS
Configure virtual links under Area 0 on both endpoints of each link.
- Virtual link A connects R3 (Router ID 10.1.1.3) and R4 (Router ID 10.1.1.4), using Area 1 as transit area.
- Virtual link B connects R4 (Router ID 10.1.1.4) and R6 (Router ID 10.1.1.6), using Area 1 as transit area.
- Use the Router ID of the remote endpoint as `neighbor-id`. Configure both sides of each virtual link.
- Run `commit check` before `commit` on each changed router.

ACCEPTANCE CRITERIA
- Each endpoint has exactly the reciprocal virtual-link statement for its neighbor.
- Transit Area 1 remains normal and has a valid, full route to each endpoint.
- No virtual link uses a stub or NSSA transit area.

TASK 3 - VERIFY BACKBONE CONTINUITY AND ROUTE PROPAGATION
On R1, R3, R4, R6 and R10, collect:
  run show ospf3 interface
  run show ospf3 neighbor detail
  run show ospf3 database extensive
  run show ospf3 route
  run show route protocol ospf3

Compare the results with Task 1. Specifically check the virtual-link adjacencies, Area 0 continuity, and remote IPv6 loopback reachability (2001:db8:ffff::1/128, ::2/128, ::3/128, ::4/128, ::6/128 and ::10/128). Use `show route <prefix> exact` if it helps identify the active route.

ACCEPTANCE CRITERIA
- Both virtual links establish OSPFv3 adjacency (Full) and are visible in operational output/LSDB where supported by the image.
- The formerly separated Area 0 portions exchange OSPF information through the R3-R4 virtual link.
- R1 can learn R2/R3-side loopbacks and R10-side Area 2 loopback through OSPFv3 after both virtual links converge.
- R10 can learn backbone-side loopbacks through OSPFv3 after both virtual links converge.
- Routes are OSPFv3-learned, not static, and the IPv6 unicast table is used.
- If cRPD rejects the statement or virtual-link neighbor state does not become Full, capture the exact `commit check` and operational outputs. Do not mark this task complete or silently replace it with static routes.

TASK 4 - EXPLAIN
Using actual output, explain:
1. Why an OSPF area other than Area 0 normally needs backbone connectivity.
2. Why the R3-R4 virtual link joins the disconnected Area 0 portions.
3. Why the R4-R6 virtual link lets the remote Area 2 become connected to the backbone.
4. Why Area 1 must remain a normal transit area with full routing information.
5. Why virtual-link endpoints are referred to by Router ID and statements must be reciprocal.
6. What the lab proves about OSPFv3 IPv6-unicast routes in `inet6.0`.

FINAL ACCEPTANCE CRITERIA
- The addressing and physical adjacency baseline is valid on all six routers.
- Both reciprocal OSPFv3 virtual links pass compatibility/commit validation and reach Full, or an exact documented cRPD limitation is captured and the feature remains marked NOT VERIFIED.
- The learner records before/after routing evidence for disconnected Area 0 and Area 2 prefixes.
- The universal topology YAML and existing br-univ are unchanged.
