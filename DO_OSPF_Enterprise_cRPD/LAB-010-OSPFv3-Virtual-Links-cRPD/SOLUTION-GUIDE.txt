LAB-010 - OSPFv3 VIRTUAL LINKS
STEP-BY-STEP SOLUTION GUIDE
Source: Junos OS OSPF User Guide, Chapter 4, “Example: Configuring OSPFv3 Virtual Links”, printed pages 159-174.

0. PRE-FLIGHT
- Stop previous OSPF labs that reuse these router interfaces/VLANs.
- Keep the universal topology and external br-univ intact.
- Complete CLEANUP-BEFORE-LAB010.txt and load the six address profiles.
- Confirm Router IDs are unique and IPv6 is configured on all links and loopbacks.
- This lab is IPv6-unicast OSPFv3 only; do not load the LAB-009 ipv4-unicast realm config.

1. BUILD PHYSICAL AREAS (NO VIRTUAL LINKS)
R1:
  set protocols ospf3 area 0.0.0.0 interface eth1.14
  set protocols ospf3 area 0.0.0.0 interface lo0.0 passive
R2:
  set protocols ospf3 area 0.0.0.0 interface eth1.23
  set protocols ospf3 area 0.0.0.0 interface lo0.0 passive
R3:
  set protocols ospf3 area 0.0.0.0 interface eth1.23
  set protocols ospf3 area 0.0.0.1 interface eth1.34
  set protocols ospf3 area 0.0.0.1 interface eth1.36
  set protocols ospf3 area 0.0.0.1 interface lo0.0 passive
R4:
  set protocols ospf3 area 0.0.0.0 interface eth1.14
  set protocols ospf3 area 0.0.0.1 interface eth1.34
  set protocols ospf3 area 0.0.0.1 interface eth1.46
  set protocols ospf3 area 0.0.0.1 interface lo0.0 passive
R6:
  set protocols ospf3 area 0.0.0.1 interface eth1.36
  set protocols ospf3 area 0.0.0.1 interface eth1.46
  set protocols ospf3 area 0.0.0.1 interface lo0.0 passive
  set protocols ospf3 area 0.0.0.2 interface eth1.610
R10:
  set protocols ospf3 area 0.0.0.2 interface eth1.610
  set protocols ospf3 area 0.0.0.2 interface lo0.0 passive

On each router run `commit check` then `commit`. Check all six physical adjacencies with:
  run show ospf3 neighbor detail
  run show ospf3 interface
  run show ospf3 database
  run show ospf3 route
Record the initial state. Do not make Area 1 a stub; it carries both virtual links.

2. CONFIGURE VIRTUAL LINK A (R3 <-> R4)
On R3:
  set protocols ospf3 area 0.0.0.0 virtual-link neighbor-id 10.1.1.4 transit-area 0.0.0.1
On R4:
  set protocols ospf3 area 0.0.0.0 virtual-link neighbor-id 10.1.1.3 transit-area 0.0.0.1
Run commit check/commit on both. Wait for the transit-area route to converge, then verify `show ospf3 neighbor detail` and `show ospf3 interface`.

Purpose: the R1-R4 Area 0 segment and R2-R3 Area 0 segment are disconnected at Area 0. The virtual link between R3 and R4 logically connects their Area 0 sides through Area 1.

3. CONFIGURE VIRTUAL LINK B (R4 <-> R6)
On R4:
  set protocols ospf3 area 0.0.0.0 virtual-link neighbor-id 10.1.1.6 transit-area 0.0.0.1
On R6:
  set protocols ospf3 area 0.0.0.0 virtual-link neighbor-id 10.1.1.4 transit-area 0.0.0.1
Run commit check/commit on both. Verify neighbor state and link-state database.

Purpose: R6 already joins Area 1 and Area 2. The virtual link logically attaches R6 to Area 0 through transit Area 1, permitting normal inter-area propagation for the remote Area 2.

4. VERIFICATION
Run where relevant:
  run show ospf3 interface
  run show ospf3 neighbor detail
  run show ospf3 database extensive
  run show ospf3 route
  run show route protocol ospf3
  run show route 2001:db8:ffff::10/128 exact
Compare R1 and R10 route visibility before versus after the two virtual links. Because cRPD CLI/output details can differ by release, verify actual route protocol/next hop rather than relying only on a specific virtual-interface name. The target is OSPFv3-learned reachability in inet6.0, not a manually installed static route.

5. EXPECTED LOGIC
- R3 and R4 must be able to route to each other through Area 1 before Virtual Link A is expected to establish.
- R4 and R6 must be able to route to each other through Area 1 before Virtual Link B is expected to establish.
- Virtual links are configured in Area 0 and refer to the remote router's Router ID, not an IPv6 interface address.
- Transit Area 1 must remain a normal area with complete routing information. Stub/NSSA transit areas cannot be used for the virtual link.
- R1/R2/R3/R4/R6/R10 Router IDs must be 10.1.1.1, .2, .3, .4, .6 and .10 respectively. Duplicate Router IDs can produce confusing neighbor/LSDB results.
- Source guide includes both OSPFv2 and OSPFv3 virtual-link examples; this lab is the OSPFv3 IPv6-unicast variant, distinct from LAB-006's OSPFv2 virtual-link exercise.

6. COMPATIBILITY NOTE
This package was authored from the Juniper guide but not live-deployed to the user's cRPD image. Do not presume feature support. If `commit check` rejects `virtual-link`, keep the exact error. If commit succeeds but the vlink fails to reach Full, capture neighbor/interface/LSDB and routing output before changing anything else. Use vJunos-router as the next feature-compatibility check; don't replace the objective with static routes.
