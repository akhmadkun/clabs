LAB-006: OSPF VIRTUAL LINKS
TASK-ONLY WORKSHEET
Image: xzjt/crpd:25.2R1-S1.4
Source: Day One: Advanced OSPF in the Enterprise, Chapter 7, "Virtual Links"

GOAL
Demonstrate why an OSPF area must connect to Area 0, observe Area 3 routes that
are not propagated into the backbone, configure a virtual link between R2 and
R10 through transit Area 2, and verify the virtual adjacency and route recovery.

BASELINE RULE
The cRPD startup configs contain interface addressing and 802.1Q VLAN tags only.
Do not add router IDs, OSPF configuration, area assignments, virtual links, or
static routes to startup configs. Configure OSPF manually during the tasks.

PHYSICAL / LOGICAL DESIGN
All router parent eth1 interfaces connect to the pre-existing host bridge
br-univ. Do not create or delete br-univ. The diagram intentionally omits it.
Logical links are carried by tagged subinterfaces:
  VLAN 12: R1 eth1.12 <-> R2 eth1.12, Area 0 (backbone, broadcast)
  VLAN 13: R1 eth1.13 <-> R3 eth1.13, Area 1 (point-to-point)
  VLAN 24: R2 eth1.24 <-> R4 eth1.24, Area 2 (transit, point-to-point)
  VLAN 410: R4 eth1.410 <-> R10 eth1.410, Area 2 (transit, point-to-point)
  Area 3: R10 eth2.0 / eth3.0 advertise 192.168.76.0/24 and 192.168.77.0/24

R2 is an ABR between Area 0 and Area 2. R10 is an ABR between Area 2 and Area 3.
R4 is a transit router within Area 2. The virtual link is configured between R2
and R10 with Area 2 as the transit area. The virtual-link endpoints must be ABRs.

TASK 0 - DEPLOY AND VERIFY ADDRESSING ONLY
1. Destroy LAB-005 before deploying this lab. Do not run OSPF labs simultaneously
   on br-univ because they reuse IP/VLAN space.
2. Confirm the host Linux bridge br-univ exists and is UP; do not remove/recreate it.
3. Run ./deploy.sh, then ./configure-hosts.sh.
4. Open cRPD Junos CLIs, for example:
     docker exec -it clab-ospf006-r1 cli
     docker exec -it clab-ospf006-r10 cli
5. On R1/R2/R3/R4/R10, inspect `show interfaces terse` and `show route protocol direct`.
6. Verify host addresses and default gateways on EP16/EP17/EP18/EP76/EP77.
7. Confirm there are no OSPF neighbors before configuring OSPF.

ACCEPTANCE CRITERIA
- All five cRPD routers use xzjt/crpd:25.2R1-S1.4 and boot successfully.
- eth1.12, eth1.13, eth1.24, and eth1.410 show the expected VLAN/IP baseline.
- R4 and R10 have the intended endpoint-facing addressing.
- EP16/EP17/EP18/EP76/EP77 have their expected IP and gateway.
- br-univ is left untouched by lab scripts, and OSPF neighbors are initially empty.

TASK 1 - BUILD AREA 0 AND AREA 1
1. Configure unique router IDs matching the loopback addresses on R1, R2, and R3.
2. Put R1 eth1.12 and R2 eth1.12 into Area 0. Keep this link as broadcast.
3. Advertise the R1/R2 loopbacks passively in Area 0. Set R1 interface priority 255
   and R2 priority 100 on eth1.12; commit R1 first on a fresh election.
4. Put R1 eth1.13 and R3 eth1.13 into Area 1 and configure both as OSPF point-to-point.
5. Advertise R3 lo0.0 passively in Area 1.
6. Verify neighbor state, router IDs, interface type, and DR/BDR on Area 0.

ACCEPTANCE CRITERIA
- R1-R2 reaches Full on Area 0; R1 is DR and R2 is BDR after a fresh election.
- R1-R3 reaches Full on Area 1 over eth1.13.
- R1 learns R2/R3 loopback reachability as appropriate for the configured areas.
- The Area 1 link is point-to-point and has no DR/BDR election.

TASK 2 - BUILD THE TRANSIT AREA 2 AND REMOTE AREA 3
1. Configure router IDs on R4 and R10 using 10.1.1.4 and 10.1.1.10.
2. Put R2 eth1.24 and R4 eth1.24 in Area 2, both point-to-point.
3. Put R4 eth1.410 and R10 eth1.410 in Area 2, both point-to-point. Area 2 must
   be a normal transit area, not a stub area.
4. Advertise R4 lo0.0 and its interfaces eth2.0/eth3.0/eth4.0 passively in Area 2.
5. Put R10 lo0.0, eth2.0, and eth3.0 passively in Area 3. The latter two interfaces
   advertise 192.168.76.0/24 and 192.168.77.0/24.
6. Verify all physical OSPF adjacencies and inspect OSPF databases on R2 and R10.

ACCEPTANCE CRITERIA
- R2-R4 and R4-R10 reach Full on Area 2.
- R10 advertises 192.168.76.0/24 and 192.168.77.0/24 in Area 3.
- R4 is the transit router between R2 and R10 inside Area 2.
- No virtual-link interface is present yet; all configured adjacencies are physical.

TASK 3 - PROVE THE BACKBONE CONNECTIVITY GAP BEFORE VIRTUAL LINK
1. On R2, inspect the route lookup for 192.168.76.0/24 and 192.168.77.0/24.
2. Inspect `show ospf route` and the Area 0/Area 2 LSDBs; note where the remote
   prefixes are or are not usable from the backbone's perspective.
3. On R1, verify that the Area 3 prefixes are not installed as OSPF routes.
4. Record the baseline output so it can be compared after adding the virtual link.

ACCEPTANCE CRITERIA
- R2 and R1 do not have active OSPF routes to the Area 3 LAN prefixes before the
  virtual link is configured.
- The R4-R10 physical adjacency is Full and R10 has the Area 3 routes locally.
- The learner can explain that Area 3 has no valid connection to backbone Area 0.

TASK 4 - CONFIGURE THE VIRTUAL LINK THROUGH AREA 2
1. On R2, configure a virtual link under Area 0 with neighbor ID 10.1.1.10 and
   transit area 0.0.0.2.
2. On R10, configure the reciprocal virtual link under Area 0 with neighbor ID
   10.1.1.2 and transit area 0.0.0.2.
3. Run `commit check`, then `commit`, on both routers.
4. Verify the virtual-link neighbor reaches Full. Inspect the virtual interface
   detail to confirm the transit area.

ACCEPTANCE CRITERIA
- Both virtual-link endpoint configurations use Area 2 (0.0.0.2) as transit area.
- R2 identifies R10 by router ID 10.1.1.10; R10 identifies R2 by 10.1.1.2.
- A virtual OSPF interface is shown on both routers and its neighbor state is Full.
- The physical Area 0, Area 1, and Area 2 adjacencies remain Full.

TASK 5 - VERIFY AREA 3 ROUTES THROUGH THE BACKBONE
1. On R2, inspect `show route 192.168.76.0/24 exact` and
   `show route 192.168.77.0/24 exact`.
2. Repeat the route checks on R1 and R3. Identify the route path type using
   `show ospf route` or `show ospf route inter` where supported.
3. Inspect the Area 0 LSDB and the R10 Router LSA detail from R2. Identify the
   virtual link entry and verify that Area 3 prefixes are now visible in OSPF.
4. Compare the results with TASK 3 and explain what changed after virtual-link
   establishment.

ACCEPTANCE CRITERIA
- R2 and R1 learn 192.168.76.0/24 and 192.168.77.0/24 through OSPF after the
  virtual link is Full; R3 also learns the prefixes through the multi-area domain.
- The routes are not external Type-5 LSAs; they are internal/inter-area routes.
- OSPF interface detail identifies a virtual interface with transit Area 2.
- The R10 Router LSA / Area 0 database shows the virtual-link relationship.

TASK 6 - END-TO-END TEST AND TROUBLESHOOTING
1. From the Linux shell of R1, ping EP76 and EP77 using R1's loopback address as
   the source IP. Example: `ping -c 3 -I 10.1.1.1 192.168.76.2`.
2. From R3's Linux shell, ping EP76 using source 10.1.1.3. cRPD in this image
   may not expose the Junos operational `ping` command; use the Linux shell.
3. If virtual link is not Full, check the router IDs, transit-area IDs, physical
   adjacencies in Area 2, and whether Area 2 is a normal (non-stub) area.
4. Explain why a virtual link is a workaround for a temporarily disconnected
   backbone and why a permanent Area 0 design is preferable.

ACCEPTANCE CRITERIA
- R1 can reach EP76 and EP77 with the source loopback specified, after routes converge.
- R3 can reach EP76 when OSPF routes are correctly installed.
- Troubleshooting isolates configuration/adjacency problems instead of adding
  static routes to hide the OSPF issue.
- The learner can explain the virtual link endpoints, transit area, and limitations.

FINAL ACCEPTANCE CRITERIA
- Addressing-only startup configs boot all five cRPD routers.
- Area 0/1/2/3 physical OSPF adjacencies are Full where expected.
- Area 3 prefixes are absent from the backbone routing view before the virtual link.
- R2-R10 virtual link is Full over transit Area 2.
- Area 3 routes propagate to R2/R1/R3 after virtual-link establishment.
- End-to-end tests from R1/R3 to EP76/EP77 succeed after convergence.
- No static route is used to mask a missing OSPF route.
