POC-002 — SOLUTION GUIDE
Palo Alto + Nexus vPC + Selective PBR
=====================================

AUDIENCE
--------
Junior engineer.

CONCEPT
-------
This lab has TWO operating modes.

MODE A — NORMAL
  Client -> Nexus SVI -> normal routing -> destination

MODE B — PBR
  Selected Client -> Nexus SVI -> PBR -> Palo Alto -> destination

The Palo Alto is physically connected in both modes. It is simply not the
forwarding path until PBR is applied.

================================================================
1. DEPLOY
================================================================

From the lab directory:

  ./preflight.sh

Then:

  containerlab deploy -t Palo_Nexus_vPC_PBR_PoC_002.clab.yml

Check:

  containerlab inspect -t Palo_Nexus_vPC_PBR_PoC_002.clab.yml

PA-VM is a VM-based vrnetlab node. Wait until PAN-OS has fully booted.

================================================================
9. PROVE THE NORMAL ROUTE
================================================================

On N9K-01:

  show ip route 10.200.200.0/24

On N9K-02:

  show ip route 10.100.100.0/24

Expected:
Connected/Local routing through Vlan200/Vlan100.

KEY IDEA:
These routes stay installed even after PBR is added.

PBR does not remove the normal route. It overrides the forwarding decision
for packets that match the route-map.

================================================================
10. PROVE PA IS NOT USED
================================================================

At this stage, open PA:

  Monitor > Traffic

Generate both test flows again.

Expected:
No firewall session for those client-to-client flows.

The PA is connected to the same VLANs, but the Nexus is performing the
normal routing.

================================================================
11. CONFIGURE PA VIRTUAL ROUTER
================================================================

Open:

  Network > Virtual Routers > Add

Name:

  VR-POC

Save.

================================================================
12. CONFIGURE PA ZONES
================================================================

Go to:

  Network > Zones

Create:

  INSIDE
  Type = Layer3

Create:

  OUTSIDE
  Type = Layer3

================================================================
13. CREATE PA AE1
================================================================

Go to:

  Network > Interfaces > Ethernet

Select:

  Add Aggregate Group

Create:

  ae1

Type:

  Layer3

Enable LACP:

  LACP Mode       = Active
  Transmission    = Fast
  Max Interfaces  = 2

Do not put the IP addresses on ae1 itself.

Palo Alto documents AE as an IEEE 802.1AX aggregate interface and supports
LACP on Layer 3 AE groups.

================================================================
14. ASSIGN AE1 MEMBERS
================================================================

Assign:

  Ethernet1/1 -> ae1
  Ethernet1/2 -> ae1

Expected:

  ae1
    + ethernet1/1
    + ethernet1/2

These physical links terminate on different Nexus vPC peers.

================================================================
15. CREATE ae1.100
================================================================

Under ae1, add a Layer 3 subinterface.

Use:

  Interface:       ae1.100
  VLAN Tag:        100
  IP:               10.100.100.254/24
  Virtual Router:   VR-POC
  Security Zone:    INSIDE

Commit later with ae1.200.

================================================================
16. CREATE ae1.200
================================================================

Add:

  Interface:       ae1.200
  VLAN Tag:        200
  IP:               10.200.200.254/24
  Virtual Router:   VR-POC
  Security Zone:    OUTSIDE

The PA is now a Layer 3 router for these two logical subinterfaces.

================================================================
22. UNDERSTAND THE PBR DESIGN
================================================================

The selected forward flow is:

  10.100.100.10
        |
        v
  N9K Vlan100
        |
        | PBR next-hop
        v
  10.100.100.254
        |
        v
  PA ae1.100
        |
      PA route/policy
        |
        v
  PA ae1.200
        |
        v
  10.200.200.10

The return flow is deliberately PBR'd too:

  10.200.200.10
        |
        v
  N9K Vlan200
        |
        | PBR next-hop
        v
  10.200.200.254
        |
        v
  PA ae1.200
        |
      PA route/state
        |
        v
  PA ae1.100
        |
        v
  10.100.100.10

Cisco documents that PBR is configured on the interface that receives the
packet, and that "set ip next-hop" selects the adjacent next hop. Traffic
that does not match the route-map continues with normal destination-based
routing.

================================================================
23. ENABLE PBR
================================================================

On BOTH Nexus switches:

  configure terminal
  feature pbr

================================================================
24. CREATE FORWARD ACL
================================================================

On BOTH Nexus:

  ip access-list ACL-PBR-TO-PA-FWD
    10 permit ip host 10.100.100.10 host 10.200.200.10

Only the selected host pair matches.

================================================================
25. CREATE FORWARD ROUTE-MAP
================================================================

On BOTH Nexus:

  route-map PBR-TO-PA-FWD permit 10
    match ip address ACL-PBR-TO-PA-FWD
    set ip next-hop 10.100.100.254

Enable statistics:

  route-map PBR-TO-PA-FWD pbr-statistics

================================================================
26. APPLY FORWARD PBR
================================================================

On BOTH Nexus:

  interface Vlan100
    ip policy route-map PBR-TO-PA-FWD

Why Vlan100?
Because traffic from 10.100.100.10 enters the Nexus routing process via
Vlan100.

================================================================
27. CREATE RETURN ACL
================================================================

On BOTH Nexus:

  ip access-list ACL-PBR-TO-PA-REV
    10 permit ip host 10.200.200.10 host 10.100.100.10

================================================================
28. CREATE RETURN ROUTE-MAP
================================================================

On BOTH Nexus:

  route-map PBR-TO-PA-REV permit 10
    match ip address ACL-PBR-TO-PA-REV
    set ip next-hop 10.200.200.254

Enable statistics:

  route-map PBR-TO-PA-REV pbr-statistics

================================================================
29. APPLY RETURN PBR
================================================================

On BOTH Nexus:

  interface Vlan200
    ip policy route-map PBR-TO-PA-REV

================================================================
30. VERIFY PBR CONFIGURATION
================================================================

Run on both Nexus:

  show ip policy

Then:

  show route-map PBR-TO-PA-FWD
  show route-map PBR-TO-PA-REV

Then:

  show route-map PBR-TO-PA-FWD pbr-statistics
  show route-map PBR-TO-PA-REV pbr-statistics

Initially counters should be zero or near zero.

Allowed session using ALLOW-INSIDE-OUTSIDE.

35. VERIFY NORMAL ROUTE STILL EXISTS
================================================================

On both Nexus:

  show ip route 10.200.200.0/24
  show ip route 10.100.100.0/24

Expected:
Connected routes remain installed.

PBR is not a route-table replacement.
It is a policy decision applied to matching ingress traffic.

================================================================
38. OPTIONAL — RETURN TO NORMAL
================================================================

To disable PBR without deleting the route-maps:

On both Nexus:

  interface Vlan100
    no ip policy route-map PBR-TO-PA-FWD

  interface Vlan200
    no ip policy route-map PBR-TO-PA-REV

Then generate:

  10.100.100.10 -> 10.200.200.10

Expected:
Traffic bypasses the PA again.

  show ip arp 10.100.100.254

  inspect ACL-PBR-TO-PA-FWD
  it must match only 10.100.100.10 -> 10.200.200.10

OFFICIAL DOCUMENTATION BASIS
================================================================

Cisco:
- Nexus 9000 NX-OS 10.3(x) Unicast Routing Configuration Guide,
  Policy-Based Routing.
  The guide documents:
    feature pbr
    match ip address
    set ip next-hop
    ip policy route-map
    PBR statistics
    PBR applied on the ingress interface.

Palo Alto Networks:
- PAN-OS 11.2 Aggregate Ethernet (AE) Interface Group
- PAN-OS 11.2 Aggregate Ethernet (AE) Interface
- PAN-OS 11.2 Layer 3 Subinterface
- VM-Series Link Aggregation Control Protocol documentation

The exact lab IPs, VLANs, vPC IDs, names, and route-map names are lab design
choices, not vendor-required values.
