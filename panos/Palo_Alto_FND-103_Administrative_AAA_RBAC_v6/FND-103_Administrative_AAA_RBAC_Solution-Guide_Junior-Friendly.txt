1. LAB OBJECTIVES
================================================================

By the end of the lab, the engineer should be able to:

1. Verify RADIUS and TACACS+ reachability from the PA-VM management plane.
2. Create a RADIUS Server Profile.
3. Create a TACACS+ Server Profile.
4. Create Authentication Profiles for RADIUS, TACACS+, and Local Database.
5. Build an Authentication Sequence in this order:
       RADIUS -> TACACS+ -> Local Database
6. Assign an administrative account to the sequence.
7. Create a least-privilege read-only Admin Role.
8. Prove that a read-only administrator cannot perform configuration writes.
9. Prove fallback behavior when RADIUS or TACACS+ is unavailable.
10. Distinguish transport failure, secret mismatch, credential failure,
    sequence behavior, and RBAC authorization failure.
11. Restore the baseline with no collateral changes.

================================================================
14. BUILD THE AUTHENTICATION SEQUENCE
================================================================

Go to:

  Device
    > Authentication Sequence
      > Add

Name:

  FND103-AUTH-SEQUENCE

Add authentication profiles in EXACTLY this order:

  1. FND103-AUTH-RADIUS
  2. FND103-AUTH-TACACS
  3. FND103-AUTH-LOCAL

Do not reverse the order.

The sequence logic is:

  User login
      |
      v
  RADIUS
      |
      +-- success --> STOP
      |
      +-- failure --> TACACS+
                         |
                         +-- success --> STOP
                         |
                         +-- failure --> Local Database
                                              |
                                              +-- success --> login
                                              +-- failure --> deny

This matches Palo Alto's documented Authentication Sequence model: the
firewall evaluates authentication profiles from top to bottom until one
successfully authenticates; access is denied when all profiles fail.

19. PROVE RBAC, NOT JUST AUTHENTICATION
================================================================

Authentication answers:
  "Who are you?"

RBAC answers:
  "What are you allowed to do?"

With `alice` logged in under FND103-READONLY:

1. Open Monitor and view operational information.
2. Open Network or Device pages and verify that information is visible.
3. Attempt to modify a harmless configuration object.
4. Attempt to commit a configuration change.
5. Attempt a CLI configuration command if CLI access is enabled by the role.

Expected:

  Operational read access = allowed
  Configuration write = denied
  Commit = denied

Do NOT use a destructive test.
Use a harmless temporary object only, then cancel/clean it up using the
break-glass administrator if needed.

20. FAILURE INJECTION 1 — RADIUS SHARED SECRET MISMATCH
================================================================

Goal:
  Distinguish an authentication failure caused by the shared secret from a
  user password failure.

Before changing anything, write ranked hypotheses. Example:

  H1  RADIUS transport unreachable
  H2  RADIUS shared secret mismatch
  H3  username/password mismatch
  H4  Authentication Profile / Allow List issue
  H5  authentication sequence order issue

Inject:

  Change ONLY the RADIUS secret on the PA-VM server profile.

Do NOT change the server container.

Test:

  test authentication authentication-profile FND103-AUTH-RADIUS username alice password

Observe:

  docker exec radius tcpdump -ni eth1 udp port 1812

Expected evidence:

  RADIUS packets still reach the server.
  Therefore transport exists.
  Authentication still fails.

The important diagnostic conclusion is:

  packet reaches server + authentication rejected
  is not the same as
  packet never reached server.

Restore the correct PA-VM secret:

  gns3

  RADIUS -> unavailable / timeout

23. FAILURE INJECTION 4 — MISLEADING SYMPTOM
================================================================

Goal:
  Learn not to conclude "bad password" from a generic login failure.

Temporarily isolate the TACACS service interface inside the TACACS container:

  docker exec tacacs ifconfig eth1 down

Now test `gns3` through the sequence.

Expected diagnostic clue:

  The user may see a generic login/authentication failure or a delayed
  fallback. The visible symptom is not sufficient to identify the root cause.

Check:

  docker exec tacacs ip -br a
  docker exec tacacs sh -c 'ss -lntp | grep 49 || netstat -lntp | grep 49'
  docker exec tacacs tcpdump -ni eth1 tcp port 49

You should recognize this as a service-path problem, not immediately as a
credential problem.

Restore the interface:

  docker exec tacacs ifconfig eth1 192.168.122.21 netmask 255.255.255.0 up

Then verify:

  docker exec tacacs ip -br a
  docker exec aa-test ping -c 3 192.168.122.21

24. DIAGNOSTIC WORKFLOW FOR JUNIOR ENGINEERS
================================================================

When authentication fails, ALWAYS work from outside to inside.

STEP 1 — Is the service path alive?

  PA-VM -> AAA IP reachable?

Commands:

  ping host 192.168.122.20
  ping host 192.168.122.21

STEP 2 — Is the correct service listening?

RADIUS:

  docker exec radius sh -c 'ss -lunp | grep 1812 || netstat -lunp | grep 1812'

TACACS+:

  docker exec tacacs sh -c 'ss -lntp | grep 49 || netstat -lntp | grep 49'

STEP 3 — Did the packet reach the server?

RADIUS:

  docker exec radius tcpdump -ni eth1 udp port 1812

TACACS+:

  docker exec tacacs tcpdump -ni eth1 tcp port 49

STEP 4 — If packets arrive, is the secret correct?

Compare the PA-VM server profile secret against the lab image's documented
client secret.

STEP 5 — Is the username present in the expected backend?

Public appliance users:

  RADIUS  : alice, bob
  TACACS+ : gns3, readonly

STEP 6 — Is the Authentication Profile Allow List blocking the user?

Check:

  Device > Authentication Profile > <profile> > Advanced > Allow List

STEP 7 — Is the Authentication Sequence in the correct order?

Expected:

  RADIUS
  TACACS+
  Local Database

STEP 8 — Did authentication succeed but authorization fail?

Then investigate RBAC / Admin Role, not AAA transport.

This distinction is critical:

  Authentication failure
      = identity was not successfully authenticated.

  Authorization/RBAC failure
      = identity authenticated, but the account lacks permission.

================================================================

The preferred first-line PAN-OS test is:

  test authentication authentication-profile <profile-name> username <username> password

Examples:

  test authentication authentication-profile FND103-AUTH-RADIUS username alice password

  test authentication authentication-profile FND103-AUTH-TACACS username gns3 password

This test can be performed against candidate configuration, so it is useful
before committing the configuration.

If the command returns an error, read it as evidence — not as a final root
cause. Palo Alto notes that network problems such as an incorrect server IP or
port may result in a non-specific error because the initial handshake never
completes.

26. COMMON FAILURE MODES IN THIS LAB
================================================================

FAILURE: ping to AAA IP fails

Likely areas:
  virbr0 attachment
  eth1 state/address
  host bridge state

Minimum evidence:
  ip -br a on the container
  ping from aa-test
  ping from PA-VM

FAILURE: ping works, RADIUS test fails immediately

Likely areas:
  wrong RADIUS port
  wrong server profile
  wrong authentication method
  shared secret mismatch
  user/Allow List mismatch

Minimum evidence:
  RADIUS tcpdump
  server listener
  PA-VM test authentication output

FAILURE: ping works, TACACS test fails immediately

Likely areas:
  wrong TCP/49 server profile
  shared secret mismatch
  CHAP/PAP mismatch
  user/Allow List mismatch

Minimum evidence:
  TCP/49 tcpdump
  TACACS listener
  PA-VM test authentication output

FAILURE: authentication succeeds but user cannot configure anything

Likely area:
  Admin Role / RBAC

This is NOT primarily an AAA transport problem.

FAILURE: fallback does not happen

Check:
  sequence order
  whether the selected administrator uses the sequence
  Allow Lists
  local database user exists
  local username exactly matches the login username

29. DESIGN / TRADE-OFF DISCUSSION
================================================================

RADIUS
------
The lab demonstrates RADIUS as one external authentication source using
UDP/1812. It is straightforward for centralized authentication, but this
exercise intentionally keeps authorization simple/local on the firewall.

TACACS+
--------
The lab demonstrates TACACS+ as a second authentication source using TCP/49.
Palo Alto documents TACACS+ support for administrative authentication and
also supports TACACS+ VSAs for external role and access-domain authorization.

Authentication Sequence
-----------------------
The sequence provides a controlled order of authentication providers. The
trade-off is that a login may take longer while unreachable external systems
time out before the next profile is attempted.

Local fallback
--------------
The local database protects access during an external identity-service
failure. The trade-off is security responsibility: the local fallback
credential becomes operationally important and must be tightly controlled in
real environments.

Least privilege
---------------
A dedicated read-only role limits what the administrator can do after
authentication. Palo Alto recommends least privilege and individual
administrator accounts rather than shared administrative identities.

================================================================
30. EXPERT EXTENSION — EXTERNAL RBAC VIA VSA
================================================================

The core lab deliberately uses local authorization because the public AAA
image is designed as a general GNS3 AAA appliance and its documented users
are not presented as a Palo Alto-specific production directory.

Once the core lab is understood, extend it with Palo Alto-specific VSAs.

Palo Alto TACACS+ VSAs include:

  service = PaloAlto
  protocol = firewall
  PaloAlto-Admin-Role = <role-name>

For a custom role, the role name on the firewall and the VSA value must match.
Palo Alto also documents VSAs for access domains and user groups.

Do NOT add VSA syntax by guessing.
Use the Palo Alto documentation and the TACACS+/RADIUS server documentation
for the exact syntax required by the backend implementation.

31. JUNIOR ENGINEER CHECKLIST — FAST REFERENCE
================================================================

When someone says:
  "AAA is broken."

Ask, in this order:

  1. Can PA-VM ping the AAA server?
  2. Is the correct port listening?
  3. Does a packet leave PA-VM / arrive at the server?
  4. Is the shared secret correct?
  5. Does the backend know the username?
  6. Does the Authentication Profile allow the username?
  7. Is the Authentication Sequence ordered correctly?
  8. Does local fallback contain the username?
  9. Did authentication succeed but RBAC deny the action?

Never jump directly to:
  "the password must be wrong."
